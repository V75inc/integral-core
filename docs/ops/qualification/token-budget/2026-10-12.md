# Native harness token-budget investigation

Date: 2026-10-12. Status: source investigation, deterministic reproductions and targeted repairs. This is not a production workload or pricing qualification. Existing unrelated checkout changes are outside this patch.

## Conclusion

The investigation baseline was **600,000 aggregate input plus output tokens per native chat turn**, with **20 model requests** and **32 successful tool calls** as separate limits. It is configurable through `INTEGRAL_NATIVE_TURN_TOKEN_LIMIT`; it is not a one-million-token default, a database transaction budget, or a model context-window size. Summary model calls share the parent run's usage and request limits. The ordinary chat path starts a fresh run allowance for each accepted turn while retaining session history.

A universal cumulative-token threshold is a blunt guard. It can stop legitimate multi-step work because repeated context counts again on every request, including cached input. However, increasing it alone would also permit more discovery loops and larger repeated payloads. The evidence supports both a workload-dependent allowance and context-efficiency work. No universal higher default has been qualified, and this patch does not change the configured allowance.

## Evidence

- The existing [qualified App count reproduction](../core-foundation-evidence/app-read-budget-summary.json) used 15 physical requests, 621,301 reported input tokens and 4,621 output tokens before the earlier discovery/read repairs. The comparable repaired run used 10 requests and 126,850 input tokens, a 79.6% observed reduction. It ended with an honest unverified-count response because the App lacked a permitted read contract. This is previous provider evidence, not a new live experiment or proof that arbitrary counts are now cheap.
- The previous [exact record lookup](../core-foundation-evidence/core-lookup-summary.json) required five physical requests and 67,259 input tokens. Its entry procedure load alone returned 19,194 bytes. Workflow instructions, catalog searches and warm history can outweigh a small data result.
- The new [offline probe](2026-10-12-probe.json) preserves all 240,000 characters from twelve synthetic current-task reads. After a typed new host event, older result characters fall to 100,147 while the five most recent pairs remain. This measures serialized text retention; it is not a billed-token estimate or a claim about model quality.
- A deterministic FunctionModel probe with synthetic usage of 40,000 input and 100 output tokens per request exhausts 600,000 at request 15 (601,500 tokens). A 1,200,000 allowance permits the same 20-request fixture to finish at 802,000. These counts are deliberately assigned test usage, not measured provider output. They demonstrate why a legitimate large working set can reach the guard before the request ceiling.
- The local Home-review installation has no usable nonzero model-usage records for this comparison. No colleague failure trace or original workload was supplied during this investigation. Attribution of those particular failures remains open.

## Confirmed defects repaired

### Cleared results were resurrected in saved working history

The inherited `ClearToolResults` hook changed request-only messages. Without a subsequent history summary, `ctx.messages`, Agent results and checkpoints still held the original completed-turn payloads. A real FunctionModel reproduction saw cleared outbound content but full content in `result.all_messages()`.

Repair: persist the completed-turn clearing projection through the public `RunContext.messages` seam. Regression coverage checks outbound messages, final messages, the actual StepPersistence snapshot, and non-mutation of the caller's original history. This preserves the canonical user transcript and archived source receipts; it changes the compacted model working context.

### Textless Core events did not establish a compaction boundary

Approval-result continuations, attachment-only uploads and scheduled events inject a new system request. Both compaction passes previously looked only for the last `UserPromptPart`, treating the previous user task and intervening host events as one indefinitely active task.

Repair: Core marks its own event with typed request metadata containing its run ID. Both compaction passes recognize that boundary. It is not inferred from prompt text, supplied by the model, or added to authored user content. The model never receives the metadata. Current event inputs and tool outcomes stay exact. Older saved unmarked events are not retrospectively guessed or relabeled.

## Remaining efficiency risks

| Path | Current behavior | Clean remediation |
| --- | --- | --- |
| Active task | All current-turn tool arguments and results remain exact, including distinct source records and mutation receipts | Introduce explicit working-context artifacts with provenance/revision and retrieval handles. Reduce source payloads before they enter context; never indiscriminately clear current grounding or an unresolved effect. |
| App/Track listings | If no cursor/limit is supplied, agent dispatch fetches every page. Per-page `MAX_LIMIT` is not an aggregate output/work bound | Return bounded projected discovery pages with truthful completeness and continuation cursors. Separate full-inventory/export jobs from conversational discovery. Update callers and tests together so partial lists cannot be presented as complete. |
| Query results | QuerySpec bounds rows, selected fields and traversal work; graph capture also has a byte budget. Row count alone does not bound string/custom-field sizes on all read tools | Extend model-facing read contracts with explicit response-byte budgets, field selection, overflow metadata and exact-record/source retrieval. Preserve the REST UI contract and authorization. |
| Procedure context | Skills remain active, loaded instructions are retained, schemas are deferred and discoveries are permission-filtered | Measure per-request instruction/schema/result dimensions and split excessively broad procedures through existing deferred capability contracts. Do not replace explicit procedures with user-intent classifiers. |
| Budget exhaustion | Token, request and tool ceilings share one public `harness_usage_limit` category and generic shorter-request/new-conversation guidance | Expose the actual exhausted dimension and consumed/allowed usage, preserve available results, and offer a fenced continuation from settled work. Retrying must not replay an uncertain effect. |
| Context vs spend | Cached tokens count toward the cumulative guard; token counts have different prices across routes. Unknown cost is preserved | Keep model-window, run-work and host monetary admission as separate policies. Route-specific context evidence and existing mandate admission own their respective enforcement. |

## Recommended budget policy

1. Keep the finite request/tool/deadline guards. Address repeated payloads and discovery before allowing more loop iterations.
2. Qualify a model-aware per-request context policy alongside the cumulative work allowance. Do not blindly enable `count_tokens_before_request` on the LiteLLM/OpenAI Chat bridge: the installed API's native pre-counting support is provider-specific, and unsupported models may raise `NotImplementedError`. A character heuristic is diagnostic, not exact billing or a model-window guarantee.
3. For a known heavy workload, **1,200,000 is a candidate operator override**, not a newly justified universal default. Validate it against representative cold/warm chats, large records, document batches, approval follow-ups and actual model usage. Increasing only this setting does not raise the 20-request/32-tool/deadline/model-window boundaries.
4. Establish p50/p95/max physical requests, input/output/cache usage, peak input, per-component characters, repeated-read ratio and completion rate for the colleagues' workloads. Compare the same task/data/model before and after source/context reductions. Never infer provider cost from missing price evidence.
5. Design a bounded completion reserve and settled-work continuation so a run approaching its allowance can report useful progress. State preservation, authorization, effect identity and billing must remain host-owned.

The installed API and current [Pydantic usage documentation](https://pydantic.dev/docs/ai/api/pydantic-ai/usage/) distinguish cumulative usage from per-request context size and include cached input. Its [compaction documentation](https://pydantic.dev/docs/ai/harness/compaction/) confirms that summary calls are charged to the parent run. Source behavior in the installed versions remains the qualification authority for this checkout.

## Validation and invariants

The four new regression probes failed in three cases before the repair and all pass afterward. The native-harness suite passes, including existing active multi-record grounding, queued-effect, skill disclosure, typed summary and scope-isolation coverage. The separately executed PostgreSQL worker/effect-fence and design-approval lanes pass all 38 tests; provider/live-model scenarios are not implied by offline tests. Formatting, import ordering and lint are checked on the touched files. These runs use the locally repaired JV Spatial source; they do not qualify a newly published dependency or a deployed stack. The full Core `make verify` gate is not rerun for this investigation.

Preserved: I-HARNESS-01 (scoped encrypted session/checkpoint namespace), I-HARNESS-02 (accepted human content unchanged and host directives separate), I-WORK-04/05 (effect identity and approval authority unchanged), I-WORK-07 (physical observations and admission unchanged), I-GRAPH-01/02 (no persisted graph entities introduced), I-EXT-01/I-SUBSTRATE-01 (generic event/context policy with no App domain logic).
