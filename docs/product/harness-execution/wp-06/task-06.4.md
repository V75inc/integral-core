# WP-06.4 — Session continuity through staging

**Status:** implemented; cross-process acceptance remains open

**Objective:** ensure native model turns, capability dispatch, staged changes,
and chat persistence use the same Core-owned session identity.

**Owned source:** `backend/app/services/chat_providers/pydantic_ai_provider.py`,
`backend/app/services/chat_streaming.py`, and the existing capability broker and
staging dispatch boundary. Do not add a parallel approval store.

**Contract:** the native provider uses the host-created `AgentRun.run_id` for
Core receipts and Pydantic persistence. Its Harness session ID is generated by
Core, written to the rooted session node, supplied to brokered capabilities,
and emitted as provider metadata before model/tool events. The existing chat
stream persists that metadata on `ChatThread` before consuming later events;
stagers resolve the thread through the same provider-session ID. Resource
authorization and approval decisions remain live Core checks.

**Acceptance:** tests demonstrate host run identity, stable session metadata,
broker session forwarding, provider-session persistence, and multi-turn
checkpoint restoration. Unresolved prior tool effects stop resumption. Temporary
materialized skill files are removed on both runtime construction and resume
failure.

**Independent qualification still required:** concurrent generation races,
approval creation and resume across process restart, duplicate decision
delivery, and the browser Prompt Sheet flow. No external model request is part
of this package.
