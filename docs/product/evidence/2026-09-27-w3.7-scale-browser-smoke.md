The fast path uses jvspatial's database `count` and sorted, limited `find`; entry exclusions are subtracted unless a direct Entry grant overrides them. Filtered queries and custom-field sorts retain their existing exact filtering path. Legacy rows missing `updated_at` also retain that path so created-time fallback order stays correct.

## In-app browser smoke

Ran the checkout backend on local port 4000 with the existing Vite UI at `http://127.0.0.1:9006`, signed in as Administrator, on `Blank Sample Check → Assets` (`n.Track.cfbdecb3a3064a10abdd6bda`). The Track table showed four entries.

- Asked “How many Assets are in this track? Please count the exact records.” The assistant used `integral_count_entries`, and its expanded browser receipt returned `total_matched: 4` and one `Assets` group with `count: 4`. The answer stated exactly four.
- Asked for the two most recently updated Assets. The browser showed links to `W39 Label Smoke` and `Smoke Search Drill`; the expanded `integral_query_entries` receipt had `limit: 2`, `total: 4`, and those two rows in timestamp order. This request included an EntryType filter and exercised the compatibility path.
- Asked for the two most recently updated entries across all open Tracks with no type or status filter. The expanded `integral_query_entries` call had only `sort_by: updated_at`, `sort_dir: desc`, and `limit: 2`; the result had `total: 10`, two newest linked rows, and a succeeded receipt. This exercised the storage-backed page path through the resident tool.

The 50,000-row timings are test-database measurements; the browser smoke confirms the resident tool and UI path on a small persisted App, not browser performance at 50,000 rows.
