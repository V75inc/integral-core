# WP-02.3 Evidence — session cleanup and export

The PostgreSQL contracts create native Harness sessions and encrypted run, event, and checkpoint records, verify owner-scoped JSON-compatible export and cross-principal denial, then invoke the same scope-checked cleanup service used by hard-delete flows. They confirm all framework payloads plus the `HarnessSession` Node and `HAS_HARNESS_SESSION` edge are removed, while the `ChatThread` remains available for its caller to finish the existing message/thread deletion sequence. The shared deletion helper checks for attached Harness sessions independently of the thread's provider field, and account/workspace deletion paths use that helper. Core `AgentRun`, `RunStep`, and usage/accounting records remain under their own retention policy.

The user-facing route `GET /chat/threads/{thread_id}/harness-sessions/{session_id}/export` resolves the authenticated owner and thread workspace before serializing a typed export. The PostgreSQL route contract verifies that the requested session matches that owner and workspace. The retention policy defaults to 90 days, is configurable from 1 to 3650 days, and deletes only aged `closed`, `expired`, or `revoked` sessions. Its transaction also verifies the owner, workspace, non-active pointer, and `HAS_HARNESS_SESSION` edge before removing encrypted Harness-private Objects and the rooted session Node. A retention probe confirms the terminal session and payload are removed while an active session and its run record are retained. ChatThread transcript and Core run/usage accounting are not included in session cleanup.

Validation on the isolated PostgreSQL 14.17 test cluster: `tests/contract/test_harness_sessions_postgres.py` plus `tests/native_harness/wp_02` pass (**25 tests**). The API response uses `HarnessSessionExport` / `HarnessSessionRunExport` schemas with extra fields forbidden. WP-02 graph reachability, encrypted tenant scope, transaction rollback, generation race, transcript reconstruction, ID collisions, key-rotation probes, owner export, hard-delete, and terminal-only retention are qualified in their respective contract tests. Repository-wide validation remains tracked in `ledger.yaml`; the known three non-harness backend failures are unchanged.
