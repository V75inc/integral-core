# From intent to an operational result

A resident interaction begins with purpose and current authorized context. It can answer, clarify, draft a design, prepare a change, or invoke an available allowed capability.

1. Establish workspace, target, and intended outcome.
2. Discover capabilities and gather authorized facts.
3. Keep a design-only request as a design.
4. Validate proposed structure, package dependencies, and schema impacts.
5. Present required review with readable scope and names.
6. Apply through the authorized execution path.
7. Report the actual result and link records or receipts for verification.

Missing capability, changed permission, revision conflict, failed migration, and uncertain external outcome are meaningful results. Do not convert them into a completion claim.

Application generation follows the package and active-definition lifecycle. It does not bypass Core by generating direct database writes. See the [white paper](WHITE_PAPER.md#15-how-software-emerges) and [user review guide](../user-guide/README.md#11-review-proposed-changes).
