# Bounded work mandate contract

Status: review schema, atomic pending-review producer and stored-approval binding reader implemented; runtime integration incomplete. No public unattended-work promise follows from schema validation.

`app.schemas.agentive.work_mandate.WorkMandateRevision` is the domain-neutral reviewed snapshot for a bounded outcome. Every nested value is frozen; collection fields become tuples. It includes server-resolved principal/workspace/thread, goal and exact input references, capability versions and targets, optional App/definition pairs, separate external destinations/credential references, model attribution, shared deadlines and finite spend/volume limits, success/stop/result obligations, bounded attempts and reconciliation-before-retry. It contains no credential material, canonical user-message replacement, mutable plan dictionary or client-approved boolean.

`review_digest()` hashes canonical JSON and normalizes equivalent time offsets and monetary representations. Scope and collection order remain part of the review. A changed goal, owner, scope, revision or limit changes the digest. The digest identifies reviewed values; it is not proof of human approval or current access. Future services must revalidate deserialized values before digest verification; unchecked `model_copy(update=...)` is not a validation boundary.

## Integration requirements

1. Resolve scope and capability versions from authenticated current Core state. Draft/schema validation cannot grant access. Store revisions immutably with approval identity/digest and normal resource authorization.
2. Reference the approved revision from existing WorkItem lineage and children. Reuse WorkApproval, lease/fence checks, work recovery and checkpoint services. Never create an App-specific scheduler or a second principal plane.
3. Before every model dispatch/tool/effect, intersect the approved grants with current permissions, capability/definition revision and provider identity. Exact resource references do not replace permission checks, relationship resolution or destination adapter validation.
4. Share durable atomic reservations and reconciled usage across children and retries. Strict USD admission requires a conservative known upper bound before dispatch; absent prices do not mean zero. Schema limits alone do not enforce spending or deadline propagation.
5. Implement fenced pause/resume/cancel on the same lineage, preserving receipts. Pause blocks new dispatch and surfaces in-flight reconciliation. Unknown external outcomes require reconciliation before any repeat. Resume rechecks current authority and remaining limits.
6. Add authenticated generic review/run/control APIs and UI. Qualify restart, lease races, revoked grants, wrong tenant/App/definition, exhaustion, in-flight pause/cancel, duplicate approvals and unknown outcomes through targeted source tests and browser flows.

`work_mandates.load_approved_work_mandate` reads the existing WorkItem and WorkApproval store. It verifies authenticated principal/workspace, snapshot/thread scope, exact plan revision and approval digest, approved status/decision/decider, App definition binding, aware decision/expiry timestamps, the mandate deadline and nonterminal/noncancelled work. A changed snapshot, copied approval from another work item, or wrong scope fails closed. It returns reviewed intent only: it does not dispatch, authorize current permissions, create an approval, reserve spending or establish child inheritance. The reviewed snapshot and approval reference live in `plan.mandate_revision` / `plan.mandate_approval_id`; `plan_revision` binds the exact digest. The internal pending-review producer described below now persists this binding. No public endpoint or executable approval path enables unattended work yet. Admission/control wiring remains required.

Current tests cover immutable snapshots, JSON round trips, required review fields, digest binding/normalization, duplicate scope rejection, finite currency limits, aware deadlines, separate external grants and App definition pairing. Stored-binding unit tests also cover wrong scope before approval lookup, digest tampering, pending/rejected/mismatched approval, expiry and terminal work. Decimal normalization is independent of process precision. They do not qualify an approved run, concurrent budget enforcement or runtime controls.

## Atomic pending review producer

`propose_work_mandate_review` accepts authenticated host principal/workspace/thread and a revalidated immutable revision. It rejects scope mismatch and expired intent before accessing storage. PostgreSQL transactions are required. It creates WorkItem, pending WorkApproval and a `work.mandate_review_proposed` outbox fact in one transaction, using deterministic owner/workspace/mandate/revision identity and the canonical digest. The WorkItem starts at `waiting_for_human`, with no lease or runnable time; no `work.enqueued` dispatch fact is emitted. Equivalent decimal/time representations reconcile the same canonical snapshot. A changed same-revision payload conflicts, requiring an explicit next revision. A retry preserves decided approval state and refuses to reconstruct a missing approval.

This is an internal persistence service, not a public authorized producer: current resource/capability/definition/provider resolution must precede eventual authenticated review exposure. The ordinary approval service rejects queueing a mandate review (`work.mandate_admission_required`); rejection and expiry remain available. A dedicated decision/admission path must verify current authority and reserve shared limits before work can run. No new worker, scheduler or App-specific branch is introduced.

Producer tests use a transaction simulator for commit, duplicate reconciliation, changed revision, semantic normalization, rollback at approval/outbox insertion, missing binding, decided retry, scope rejection, expiry, transactional-store requirement and approval bypass denial. They are source evidence. Separate PostgreSQL contracts verify concurrent duplicate proposals with committed store readback, rollback after WorkApproval or outbox insertion failure, denial of ordinary executable approval, durable rejection and reconciliation of a decided retry. All 64 selected mandate/approval tests pass in disposable PostgreSQL mode (`/tmp/venture-mandate-producer-postgres-final.log`), including those four real-store cases. This does not prove process-crash recovery, shared budget admission or browser acceptance. The full Core `make verify` gate passed with exit 0 (`/tmp/venture-mandate-producer-full-verify.log`), including 1,521 frontend tests, the backend suite and CI reproduction. The default full gate skips PostgreSQL contracts; the separate 64-test PostgreSQL run supplies the store evidence above. Optional external-infrastructure skips remain outside this proof.


## Root and child review lineage

`load_approved_mandate_lineage` resolves up to 32 existing WorkItems through exact parent links. It reads WorkItem and WorkApproval documents directly from the active durable store, bypassing identity caches. Every ancestor must match authenticated principal/workspace/thread and remain active and uncancelled. Children carry `plan.mandate_root_work_item_id` and the root's exact `plan_revision`, never a copied snapshot or approval. Their aware deadlines may shorten but cannot extend the parent's remaining deadline. Missing parents, cycles, changed roots/digests, copied authority, inactive ancestors and expired deadlines fail closed. The root must retain the exact approved snapshot/binding.

This service neither creates children nor dispatches them. A sequence of reads is not a transaction fence. Runtime admission still needs root/child locking and lease authority, current resource/capability/definition/provider checks, shared durable reservations, controls and reconciliation. A synthetic approved-store fixture tests reading and invalidation only; it does not enable public executable approval or qualify unattended work. The selected mandate/approval suite passes all 90 cases in disposable PostgreSQL mode (`/tmp/venture-mandate-lineage-postgres.log`), including the actual-store lineage readback and cache-invalidation case. Synthetic approval seeding is test setup, not executable-admission proof. The full Core `make verify` gate passed with exit 0 (`/tmp/venture-mandate-lineage-full-verify.log`), including 1,521 frontend tests, backend tests and CI reproduction. Optional external-infrastructure skips remain; PostgreSQL evidence comes from the separate selected run.


## Shared-budget integration contract (dispatch wiring incomplete)

The inspected dispatch locations are `capability_broker.invoke` for tools and `LiteLLMSDKTransport.handle_async_request` before `_sdk_completion` for physical model requests. `work_items.authorized_work_item_effect` supplies the existing child lease/fence transaction for internal effects. Post-response model observations are usage evidence; they cannot provide pre-dispatch admission or prove a price was known before an operation started. No new provider retry loop is needed: the transport already disables SDK retries.

Use one durable account keyed by approved root WorkItem and review digest, plus deterministic reservation records keyed by root/child/logical effect identity. Every child and retry draws from that account. Reserve spend and relevant model/tool/write/external counts atomically; duplicate identical reservation delivery returns the same record without charging again, while a changed operation, provider, credential attribution, input fingerprint or upper bound conflicts. Preserve per-capability call limits as well as global counters. Money uses exact fixed decimal units with the review's USD precision; process decimal context and floating-point arithmetic must not change admission.

Before dispatch, recheck authenticated lineage, current grants/definition/provider and lease/root controls under the corresponding durable transaction fence. An upper-bound quote must identify the exact resolved provider/model/credential attribution and pricing basis, bound input/output/retries, and remain valid through admission. Missing/unavailable prices are not zero. A promised monetary cap cannot silently fall back to volume-only limits or the observed cost after the call.

Reservations transition from reserved to settled only with attributable terminal usage evidence. Confirmed no-dispatch can release its reservation; uncertain provider/effect outcomes keep the conservative hold and require reconciliation before a retry. Settled usage and unreconciled holds both reduce remaining budget. Overrun or invalid usage is an incident/stop condition, not a negative counter or an automatic refund. Pausing/cancelling blocks new admission and retains already-dispatched reservations until their outcomes are known.

Acceptance must demonstrate competing children cannot oversubscribe, duplicate deliveries and process restarts reconcile the same reservation, forged scope/provider/quote is denied, exact exhaustion blocks before dispatch, permission revocation and in-flight cancellation are fenced, unknown outcomes never refund or repeat prematurely, and unavailable-price requests produce an honest founder-visible hold. Source ledger tests alone cannot qualify the harness wiring or the browser experience.


## Shared reservation storage implementation

`work_budgets.reserve_mandate_budget` now stores a deterministic WorkBudgetReservation fact and root-shared integer counters in one PostgreSQL graph transaction. The existing root WorkItem row serializes competing children. Known upper-cost holds and charged usage jointly reduce the cap; model/tool counts, host-derived batch write/external-effect volumes and per-capability/destination limits are checked before a reservation is stored. Exact reviewed model route/credential and capability/destination snapshots are required. Decimal values use fixed 1e-8 USD units independent of ambient precision. Duplicate identical requests reconcile; changed fingerprints conflict. Review retries retain mutable ledger counters while checking the exact immutable snapshot/approval binding.

`settle_mandate_budget` records attributable terminal usage and releases only the difference between the known charge and its conservative hold. Request counts remain consumed. Unknown costs/outcomes keep holds. Settlement can complete after root cancellation; a quoted-bound overrun is retained as usage and requests a root stop. Duplicate settlement cannot charge twice; changed receipt/cost conflicts. Separate reservation facts keep the root ledger bounded in size.

These are internal accounting services, not executable admission. The caller must be a trusted host price/terminal-usage resolver; this schema alone does not verify pricing, receipt provenance or actual operation targets. No public tool/API or harness hook exposes them. Lease/root/child dispatch fencing, current permissions, quote verification, confirmed no-dispatch release, process restart recovery, price/usage incident handling and browser controls remain required. The existing browser deployment is unchanged. All 108 selected mandate/approval/budget tests pass in disposable PostgreSQL mode (`/tmp/venture-mandate-budget-replay-postgres.log`), including 17 actual-store ledger cases covering concurrency, duplicate reservation/settlement, fresh-context reconciliation, unknown price/outcome holds, cancellation, overruns, exact attribution, rollback and batch/global/per-capability limits. Synthetic quotes and seeded approvals are fixtures, not provider-price or dispatch proof. The final full Core `make verify` gate passed with exit 0 (`/tmp/venture-mandate-budget-final-verify.log`), including 1,521 frontend tests, the full backend suite and CI reproduction. Optional infrastructure skips remain; PostgreSQL evidence is supplied by the separate selected run.

Stored reservation replay and settlement revalidate identity, canonical request digest, exact quoted cost hold, terminal-state coherence and authenticated scope. Replay also checks the approved model/capability/destination snapshot again and refuses an absent cost hold. Tampered-record cases include a coherently forged request and digest; none can widen reviewed authority. These checks do not replace trusted price/receipt resolution or atomic dispatch admission.

Invariant preservation: I-GRAPH-02 uses Object coordination records rather than domain Nodes; I-CRUD-01 keeps all mutations in services; I-SUBSTRATE-01 contains no founder policy. I-WORK-02 retains deterministic logical-effect identity and rejects changed requests; I-WORK-03 commits reservation facts and counters atomically; I-WORK-06 requires the transactional PostgreSQL store. I-WORK-01 and I-WORK-05 remain unchanged: this accounting service does not grant lease authority or make pending mandate reviews executable.

External-effect counters currently aggregate by capability and apply the selected reviewed destination limit. This is conservative across multiple destinations, not independent destination accounting. Add separate destination counters and multi-destination acceptance before exposing that broader mandate shape.
